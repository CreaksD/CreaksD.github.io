## 第一章 MySQL 基础 (0:40 – 3:30)

### 1.1 IN vs EXISTS (0:40 – 2:10)

**[画面]** 屏幕左右分屏：左边 `user` 表，右边 `order` 表，数据高亮。

**口播**
「先从最简单的说起。SQL 里 `IN` 和 `EXISTS` 都能做子查询，但思维方式完全不同。`IN` 是『拿这个值去集合里查』，`EXISTS` 是『子查询能找到一条记录就行』。记住这一句话，后面全通了。」

**[画面]** 两张表并排展示，用动画演示查询过程。

**例子**
```
user 表                    order 表
+----+--------+           +----+---------+
| id | name   |           | id | user_id |
+----+--------+           +----+---------+
| 1  | 张三   |           | 1  | 1       |
| 2  | 李四   |           | 2  | 1       |
| 3  | 王五   |           | 3  | 2       |
+----+--------+           +----+---------+
```

**口播（配动画）**
「看这个经典例子：查『有订单的用户』。用 `IN` 写，子查询先把 order 表的 user_id 全部取出来，得到集合 [1, 1, 2]，然后判断 user.id 在不在集合里——张三 1 号在，李四 2 号在，王五 3 号不在，所以返回张三和李四。」

**[画面]** 代码高亮 + 箭头动画：`order.user_id → 集合[1,1,2] → user.id IN 集合? → 1、2 符合`。

```
SELECT * FROM user
WHERE id IN (
    SELECT user_id FROM `order`
);
```

**口播**
「用 `EXISTS` 写，逻辑反过来：拿起外层的张三（id=1），问 order 表里有没有 user_id=1 的记录？有，返回 TRUE。再拿李四，有。拿王五，没有，FALSE。注意，`EXISTS` 是**只要找到一条匹配就立即停**，不扫完整个子查询结果。」

**[画面]** 逐行演示：张三→有→TRUE；李四→有→TRUE；王五→没有→FALSE。

```
SELECT * FROM user u
WHERE EXISTS (
    SELECT 1 FROM `order` o
    WHERE o.user_id = u.id
);
```

**口播**
「所以性能上：子查询结果集很大时，`EXISTS` 通常更快，因为它一找到匹配就停止；而 `IN` 可能要把整个子查询结果算完。当然，优化器也可能做改写，不能绝对化。怎么记场景？`IN` 适合『集合判断』——id 是否属于 [1,2,3,4]；`EXISTS` 适合『关联存在性判断』——只要存在订单就把用户查出来。」

### 1.2 NULL 与三值逻辑（NOT IN 的经典坑）(2:10 – 3:00)

**[画面]** 一个大红感叹号 + 标题：「NOT IN + NULL = 面试送命题」

**口播**
「接下来是 SQL 里最容易被忽略的坑：**三值逻辑**。SQL 里比较的结果不只是 TRUE 和 FALSE，还有 UNKNOWN——只要碰了 NULL，就是 UNKNOWN。看这个例子：`3 NOT IN (1, 2, NULL)` 实际上等价于 `3 != 1 AND 3 != 2 AND 3 != NULL`。」

**[画面]** 逐步展开算式，最后一行高亮红色。

**例子**
```
3 NOT IN (1, 2, NULL)
= 3 != 1 AND 3 != 2 AND 3 != NULL
= TRUE  AND TRUE  AND UNKNOWN
= UNKNOWN            ← WHERE 只保留 TRUE，这条被丢弃！
```

**口播**
「前两个是 TRUE，但 `3 != NULL` 是 UNKNOWN，TRUE AND TRUE AND UNKNOWN 结果是 UNKNOWN。而 WHERE 子句只保留 TRUE——所以这条记录**直接被丢弃**了。这就是为什么 `NOT IN` 子查询里一旦混进 NULL，结果就神秘地少数据。同理，`1 = NULL` 是 UNKNOWN，`NULL = NULL` 也是 UNKNOWN——NULL 不能当普通值理解。」

**[画面]** 展示一张真值表（AND/OR 与 UNKNOWN 的组合），再展示坑场景：`WHERE id NOT IN (SELECT user_id FROM order)`，如果 user_id 里有 NULL，你想查出的 3、4、5 全没了。

## 第二章 存储引擎与数据文件 (3:30 – 5:30)

### 2.1 InnoDB vs MyISAM (3:30 – 4:45)

**[画面]** 两个引擎拟人化对打动画，左边 InnoDB 全副武装，右边 MyISAM 轻装上阵。

**口播**
「面试必问：InnoDB 和 MyISAM 有什么区别？记住四个维度就够了——事务、索引、锁粒度、count 效率。InnoDB 支持事务、支持行锁，数据按主键聚簇存放；MyISAM 不支持事务、只有表锁，数据文件分离。这也是为什么 MySQL 后来把默认引擎从 MyISAM 换成了 InnoDB——为了事务和并发。」

**[画面]** 一张对比表格逐行点亮，每行配一个小动画（锁的图标、事务图标）。

**例子**
| 维度 | InnoDB | MyISAM |
| --- | --- | --- |
| 事务 | ✅ 支持（ACID） | ❌ 不支持 |
| 索引结构 | 聚簇索引，叶子节点存完整数据 | 非聚簇索引，索引存数据指针 |
| 锁粒度 | 行锁（最小） | 表锁（最小） |
| `COUNT(*)` | 全表扫描 | 直接读变量，极快 |
| 崩溃恢复 | ✅ redolog 恢复 | ❌ 不支持 |
| 适用场景 | 高并发读写 | 大量只读场景 |

**口播**
「注意两个细节：第一，InnoDB 的辅助索引要先查到主键、再回表查数据，所以主键不能太大，否则其他索引也都被撑大；第二，MyISAM 用变量保存行数，count 飞快，但 InnoDB 每次都要全表扫——这是有得必有失。」

### 2.2 数据文件三件套 (4:45 – 5:30)

**[画面]** 终端画面：`ls /var/lib/mysql/my_test`，显示三个文件。

**口播**
「表建好之后，磁盘上到底存了什么？进到数据库目录看一眼：一个库文件夹里通常有这三个文件。」

**[画面]** 终端输出高亮三个文件名，每个配一行解释。

**例子**
```
/var/lib/mysql/my_test/
├── db.opt         → 数据库默认字符集和校验规则
├── t_order.frm    → 表结构定义（元数据）
└── t_order.ibd    → 表数据 + 索引（独占表空间）
```

**口播**
「`db.opt` 存字符集配置；`.frm` 存表结构；`.ibd` 存数据。从 MySQL 5.6.6 开始，`innodb_file_per_table` 默认开启，每张表的数据都独立存在自己的 `.ibd` 文件里，而不是挤在共享表空间 `ibdata1` 中。这个参数面试常聊，记住默认值是 1。」

### 3.2 B+Tree 索引结构 (6:10 – 7:20)

**[画面]** 一棵三层 B+Tree 动画：根节点 [1|10|20]，中间层，叶子层双向链表。

**口播**
「InnoDB 的索引用 B+Tree 实现。它是一棵多叉树：**叶子节点才存数据，非叶子节点只存索引**，而且每个节点里的 key 按主键顺序排列，每层父节点的索引值都出现在下层子节点里——所以叶子节点包含了全部索引值。更关键的是：每个叶子节点有两个指针，指向前后叶子节点，串成一条**双向链表**。这条链表就是范围查询快的秘密。」

**[画面]** 演示查询 `SELECT * FROM product WHERE id = 5` 的路径：根节点 [1,10,20] → 5 在 1 和 10 之间 → 第二层 [1,4,7] → 5 在 4 和 7 之间 → 叶子 [4,5,6] → 命中 id=5。

**口播**
「查 id=5 的过程：跟根节点的 (1,10,20) 比较，5 在 1 和 10 之间，下到第二层；在 (1,4,7) 里找，5 在 4 和 7 之间，再到叶子层 (4,5,6)，命中。读取一个节点就是一次磁盘 I/O，整个过程只用了 3 次 I/O——这就是 B+Tree 最牛的地方：**千万级数据，树高只有 3~4 层，查询永远只要 3~4 次磁盘 I/O**。相比之下，B 树每个非叶子节点都存数据，层数更多，二叉树就更不用说了。」

**[画面]** 对比动画：B+Tree 三层 vs B 树多层 vs 二叉树更多层，突出「矮胖」优势。

**口播**
「再补三个特性：所有叶子节点在同一层，查询延迟一致；非叶子节点只存键值，所以树更矮；树是自平衡的，插入删除后自动调整，保证高度稳定。」

### 3.3 聚簇索引 vs 二级索引：三棵树的比喻 (7:20 – 8:30)

**[画面]** 建表 SQL + 三棵树并排动画。

**口播**
「现在看 InnoDB 最核心的设计。一张表通常有**多棵 B+Tree**：如果建了主键，主键索引树叫**聚簇索引**，它的叶子节点存的是**完整的数据行**；每建一个二级索引，就多一棵**二级索引树**，叶子节点只存『索引列 + 主键值』。比如说这张用户表：」

**[画面]** 展示例子表格 + 三棵树结构图。

**例子**
```
CREATE TABLE user (
    id BIGINT PRIMARY KEY,      -- 聚簇索引树
    name VARCHAR(50),
    age INT,
    city VARCHAR(50),
    email VARCHAR(100),
    INDEX idx_age(age),         -- 第二棵树
    INDEX idx_city(city)        -- 第三棵树
);

数据：
id  name  age  city
1   张三  20   北京
2   李四  30   上海
3   王五  20   北京

主键索引树（聚簇）       age 索引树（二级）      city 索引树（二级）
叶子: 完整记录            叶子: age→主键id         叶子: city→主键id
id=1 → (1,张三,20,北京)   age=20 → id=1,3         北京 → id=1,3
id=2 → (2,李四,30,上海)   age=30 → id=2           上海 → id=2
id=3 → (3,王五,20,北京)
```

**口播**
「注意二级索引的叶子节点：`age=20` 下面存的是主键 `id=1` 和 `id=3`，不是完整记录。这带来两个重要概念——覆盖索引和回表。查询 `SELECT id, age WHERE age = 20`：id 和 age 在二级索引里都有，直接返回，**不需要再碰主键索引**，这就是**覆盖索引**，最快的路径之一。」

**[画面]** 第一个查询动画：idx_age → age=20 → id=1,3 → 直接返回（绿色对勾）。

**口播**
「但如果查询变成 `SELECT id, age, name WHERE age = 20`：name 不在 age 索引里。数据库只能先走 idx_age 拿到 id=1，**回到主键索引**找完整记录取出 name，再重复一次拿 id=3 的记录——这个『先二级索引、再回主键索引』的过程就叫**回表**。回表越多越慢，所以设计索引时尽量让查询走覆盖索引。」

**[画面]** 第二个查询动画：idx_age → id=1 → 回主键树 → 取 name=张三（红色折线箭头，标注「回表」）。

### 3.4 联合索引与最左匹配 (8:30 – 9:30)

**[画面]** 一棵联合索引树，key 是 (product_no, name) 两列。

**口播**
**「联合索引是面试的高频考点。联合索引的 B+Tree 先按第一个字段排序，第一个字段相同再按第二个字段排序——所以它天生遵守最左匹配原则。比如建了 (a,b,c) 联合索引：`WHERE a=1`、`WHERE a=1 AND b=2`、`WHERE a=1 AND b=2 AND c=3` 都能用上；但 `WHERE b=2`、`WHERE c=3`、`WHERE b=2 AND c=3` 全部失效。」**

**[画面]** 左边三行绿色（能用），右边三行红色（失效），字幕解释原因：b 和 c 全局无序、局部有序。

**例子**
```
索引：(a, b, c) 联合索引
✅ 能命中：WHERE a=1
✅ 能命中：WHERE a=1 AND b=2
✅ 能命中：WHERE a=1 AND b=2 AND c=3
❌ 失效：  WHERE b=2
❌ 失效：  WHERE c=3
❌ 失效：  WHERE b=2 AND c=3

（注意：查询优化器会调换 a 的条件位置，a 在 WHERE 里的书写顺序不影响）
```

**口播**
「另外提醒：建了单列索引 a 又建了联合索引 (a,b)，单独查 a 时到底走哪个？MySQL 优化器会估算每个索引的查询成本，**选成本最低的方案**，不是死的。」

### 3.5 索引失效的六种情况 (9:30 – 10:15)

**[画面]** 六张红色警示卡片逐个弹出。

**口播**
「面试另一大考点：索引什么时候会失效？一共六种，一个一个来——」

**[画面]** 每张卡片配一句 SQL 示例。

**例子**
```
1. 左模糊 / 左右模糊：LIKE '%xx' 或 LIKE '%xx%'
2. 对索引列使用函数：WHERE SUBSTR(name,1,1)='张'
3. 对索引列做表达式计算：WHERE id+1 = 10
4. 隐式类型转换（内部走 CAST 函数，等于对索引列用了函数）：
   索引列是字符串，条件传数字
5. 联合索引不满足最左匹配
6. OR 连接的某个列没有索引 → 通常全表扫描
```

**口播**
「口诀帮你记：**模糊、函数、计算、隐式转换、不最左、OR 缺索引**。另外 MySQL 5.1 之后有 index_merge 优化，OR 多索引有时能合并读取，但依赖数据分布和优化器成本估算，别当保险。」

### 3.6 页目录：叶子节点内部怎么找 (10:15 – 11:00)

**[画面]** 一个数据页内部结构图：记录分组 + Page Directory 槽。

**口播**
「最后解答一个很多人卡住的点：B+Tree 找到了叶子节点，但叶子节点里还有几百条记录，怎么快速定位？答案是**页目录**。InnoDB 的一个叶子节点对应一个数据页，页里记录按主键排序后分组，每组最后一条记录是组内最大记录，页目录只记录每组最大记录的偏移量，这些偏移量就是槽。查找时用**二分法**先定位到槽，再在组内顺序遍历。」

**[画面]** 动画演示：15 条记录分 5 组，槽 0~4 分别指向 3、6、8、12、15，查找 id=11 的过程。

**例子**
```
记录分组：  组0: 1,2,3 | 组1: 4,5,6 | 组2: 7,8 | 组3: 9,10,11,12 | 组4: 13,14,15
Page Directory（槽）： Slot0→3  Slot1→6  Slot2→8  Slot3→12  Slot4→15

查找 id=11：
① 二分 (0+4)/2=2 → Slot2 最大是 8，11>8，去后半段
② 二分 (2+4)/2=3 → Slot3 最大是 12，11<12，定位到组 3
③ 从组 3 的最小记录 9 往下数 2 次 → 命中 11
```

**口播**
「三步就找到，不用从页头遍历整个链表。这就是为什么 InnoDB 在千万级数据下依然快——**索引负责快速定位数据页，页目录负责在页内快速定位记录**，两层机制缺一不可。」

### 3.7 索引的优缺点与建索引原则 (11:00 – 11:30)

**[画面]** 天平动画：左边「快」，右边「空间/写性能」。

**口播**
「索引不是越多越好。好处是查询快，代价有三：占物理空间；创建和维护耗时；**降低增删改效率**——每次写操作都要维护 B+Tree 的有序性。什么时候该建索引？有唯一性约束的字段（如商品编码）、经常出现在 WHERE 里的字段、经常 GROUP BY / ORDER BY 的字段。反过来，数据量大时更新索引数据，B+Tree 还要重新调整结构。」

## 第四章 事务 (11:30 – 15:30)

### 4.1 ACID 与并发三大问题 (11:30 – 13:00)

**[画面]** 标题：「事务的四大特性和三个并发陷阱」。ACID 四个字母卡片。

**口播**
「接下来是事务。InnoDB 靠什么保证 ACID 四大特性？一句话对应一个机制：**持久性靠 redolog，原子性靠 undolog，隔离性靠 MVCC 或锁，一致性是前三者合力保证的**。记住这个对应关系，很多题都能答。」

**[画面]** 四组对应关系动画。

**例子**
```
持久性 Durability  → redolog（重做日志）
原子性 Atomicity   → undolog（回滚日志）
隔离性 Isolation   → MVCC 或锁机制
一致性 Consistency → 持久性 + 原子性 + 隔离性 共同保证
```

**口播**
「为什么需要隔离？因为并发会带来三个经典问题，都是『小林余额』的故事。第一个：**脏读**。事务 A 改了小林余额 100 万变 200 万但没提交，事务 B 就读到了 200 万；结果 A 回滚了，B 拿到的是过期数据——这就是脏读，读到别人未提交的数据。」

**[画面]** 使用 image/脏读.webp 动画化，时间线演示 A 改未提交、B 读到、A 回滚。

**口播**
「第二个：**不可重复读**。一个事务内两次读同一行，中间另一个事务提交了修改，前后读到的值不一样。A 第一次读余额 100 万，B 更新成 200 万并提交，A 第二次读变成了 200 万。」

**[画面]** 使用 image/不可重读.webp，时间线演示两次读取值不同。

**口播**
「第三个：**幻读**。一个事务内两次查询『余额大于 100 万』的记录，第一次查到 5 条，B 插入一条余额 200 万的记录并提交，第二次查询变成 6 条——多出来的记录像幻觉一样。注意区分：不可重复读是**同一行值变了**，幻读是**记录条数变了**。」

**[画面]** 使用 image/幻读.webp，两次数数的动画，5 条 → 6 条。

### 4.2 四种隔离级别 (13:00 – 14:00)

**[画面]** 四级台阶图，从下往上：读未提交 → 读已提交 → 可重复读 → 串行化。

**口播**
「为了解决这些问题，SQL 定义了四种隔离级别，从松到严：**读未提交**——能读到别人未提交的数据，脏读不可重复读幻读全都有；**读已提交**——提交后变更才可见，解决了脏读；**可重复读**——事务执行过程中看到的数据始终跟启动时一致，解决了不可重复读，MySQL InnoDB 的默认级别；**串行化**——读写冲突直接排队，全解决但并发最差。读已提交和可重复读其实还有幻读问题，InnoDB 在可重复读下靠**间隙锁**额外解决了幻读，这个后面锁的章节讲。」

**[画面]** 表格逐行出现，标注 InnoDB 默认是「可重复读」。

**例子**
| 隔离级别 | 机制 | 脏读 | 不可重复读 | 幻读 |
| --- | --- | --- | --- | --- |
| 读未提交 Read Uncommitted | 直接读最新数据 | 可能 | 可能 | 可能 |
| 读已提交 Read Committed | MVCC + 每条语句创建 Read View | 避免 | 可能 | 可能 |
| 可重复读 Repeatable Read（InnoDB 默认） | MVCC + 事务首个 SELECT 创建 Read View | 避免 | 避免 | 基本避免（靠间隙锁） |
| 串行化 Serializable | 加读写锁排队 | 避免 | 避免 | 避免 |

**口播**
「Java 开发者注意，你不需要手动管 Read View——Spring 的 `@Transactional(isolation = Isolation.REPEATABLE_READ)` 注解，最终通过 JDBC Connection 执行 `SET TRANSACTION ISOLATION LEVEL REPEATABLE READ`，把活儿交给 MySQL。生产环境最常见的就两个：RC 和 RR，它们都依赖 MVCC + Read View。」

### 4.3 MVCC 与 Read View (14:00 – 15:30)

**[画面]** 照相机拍照动画，定格瞬间，引出 Read View 概念。

**口播**
「MVCC 全称多版本并发控制，核心思想：一行数据在数据库里保存多个版本，事务读取时选择**自己该看到的版本**，互不阻塞，实现非阻塞读。而决定『该看到哪一版』的，就是 **Read View**——你可以把它理解成拍立得相机，拍下的那一刻，定格了当时的数据风景。」

**[画面]** 使用 image/readview结构.webp，展示 Read View 四个字段。

**口播**
「Read View 有四个核心字段，面试必背：`m_ids`——创建时活跃（启动未提交）事务的 id 列表；`min_trx_id`——m_ids 里的最小值；`max_trx_id`——创建时下一个要分配的事务 id（注意不是 m_ids 的最大值）；`creator_trx_id`——创建这个 Read View 的事务自己的 id。」

**[画面]** 四字段卡片逐个点亮。

**例子**
```
Read View 四个字段：
m_ids            → 活跃未提交事务的 id 列表
min_trx_id       → m_ids 中的最小值
max_trx_id       → 下一个待分配的事务 id（≠ m_ids 最大值）
creator_trx_id   → 创建 Read View 的事务自身 id
```

**口播**
「RC 和 RR 的区别就在于 Read View 的创建时机：**读已提交**是每条 SELECT 语句执行前都重新生成一个 Read View，所以同事务两次 SELECT 可能看到不同版本；**可重复读**是事务执行第一条 SELECT 时生成一个，整个事务都用这一个——这就是它俩名字的由来，也是『可重复读』名字的含义。记不住的话：RC 是『每句话拍一张照』，RR 是『整场只拍一张照』。」

**[画面]** 两个相机动画对比：RC 连续咔咔咔，RR 只咔一次。

## 第五章 锁 (15:30 – 18:30)

### 5.1 锁的分类：全局锁、表级锁、行锁 (15:30 – 16:20)

**[画面]** 三层同心圆图：最外层全局锁，中层表锁，内层行锁。

**口播**
「按加锁范围，MySQL 的锁分三类。**全局锁**：`FLUSH TABLES WITH READ LOCK` 让整个库只读，主要用于全库逻辑备份，防止备份期间数据不一致。**表级锁**：包括表锁、元数据锁 MDL、意向锁。MDL 最值得说——对表做 CRUD 时加 MDL 读锁，改表结构时加 MDL 写锁，防止你查询时别人把表结构改了。注意一个经典事故：一条慢查询一直持有 MDL 读锁，后面所有改表结构的写锁排队，再后面的查询全被堵死。**行级锁**：InnoDB 专属，MyISAM 没有。」

**[画面]** MDL 死锁排队动画：慢查询 → MDL 读锁不释放 → 写锁排队 → 新查询全阻塞。

### 5.2 记录锁 / 间隙锁 / 临键锁 (16:20 – 17:30)

**[画面]** 一张 account 表，数据 id 为 1、3、5、8、10。

**口播**
「行锁里最常考的是三兄弟：记录锁、间隙锁、临键锁。先说**记录锁**：`UPDATE account SET name='XXX' WHERE id=5`，主键定位，锁住 id=5 这一条。另一个事务改 id=5 会被阻塞，但改 id=3 不受影响。」

**[画面]** id=5 高亮加锁图标，演示阻塞与不阻塞两条 UPDATE。

**口播**
「但注意，表里 id 有 1、3、5、8、10，中间有空位。如果执行 `SELECT * FROM account WHERE id>3 AND id<5 FOR UPDATE`——没有记录符合条件，但 InnoDB 在可重复读下会锁住 **(3,5) 这个区间**，这就是**间隙锁**。它锁的是不存在的『空气』。为什么要锁空气？防止幻读——如果 T2 在 (3,5) 里插入 id=4，T1 第一次查空、第二次查到 4，条数变了，幻读就出现了。」

**[画面]** 数轴上 (3,5) 区间涂色，插入 id=4 的动画被红色禁止符号拦截。

**口播**
「**临键锁**就是记录锁加间隙锁的组合，锁住一个左开右闭区间，比如 (1,3]，既能防止修改删除，也能防止插入。总结：**间隙锁防插入，记录锁防改删，临键锁两个都防**。」

**[画面]** 公式动画：`Next-Key Lock = Record Lock + Gap Lock`，数轴演示 (1,3]。

**例子**
```
account 表：id = 1, 3, 5, 8, 10

记录锁 Record Lock    → UPDATE ... WHERE id=5  → 锁住已存在的 id=5
间隙锁 Gap Lock       → SELECT ... WHERE id>3 AND id<5 FOR UPDATE
                      → 锁住不存在的区间 (3,5)，防止插入 id=4
临键锁 Next-Key Lock  → 记录锁 + 间隙锁，如 (1,3]，两个都防
```

### 5.3 无索引 UPDATE 为什么危险 (17:30 – 18:30)

**[画面]** 红色警报标题：「UPDATE 没走索引 = 变相锁全表」

**口播**
「回到开头的那个线上事故。`UPDATE account SET name='XXX' WHERE age=20`，如果 age 没有索引，InnoDB 只能全表扫描判断每条记录 age 是不是 20。而**锁定读和 UPDATE 在扫描过程中，扫到的每条索引记录都要加锁**——于是 1、3、5、8、10 全被锁上了，表现得跟锁全表一样。」

**[画面]** 五条记录逐个亮起 🔒。

**口播**
「更要命的是第二个事务哪怕更新 age=25 的**不同数据**，它也要全表扫描，扫到第一个事务锁住的记录就卡住了。两个毫不相干的 UPDATE 互相阻塞——这就是无索引 UPDATE 在并发场景下的连环坑。所以生产环境两个铁律：**UPDATE/DELETE 的 WHERE 条件必须走索引**；锁要能查到、更要能想清楚它扫了多远。」

**[画面]** T1 锁全表动画 + T2 阻塞转圈动画，字幕：「不同行，也会互相堵」。

## 第六章 日志 (18:30 – 22:30)

### 6.1 四大日志总览 (18:30 – 19:15)

**[画面]** 一张 MySQL 架构分层图，Server 层和 InnoDB 层分别挂出日志。

**口播**
「日志是 MySQL 可靠性的根基，一共四类：**redo log** 重做日志，InnoDB 层，实现持久性，掉电恢复靠它；**undo log** 回滚日志，InnoDB 层，实现原子性，回滚和 MVCC 靠它；**binlog** 二进制日志，Server 层，所有引擎共用，备份和主从复制靠它；**relay log** 中继日志，主从复制里 slave 从 master 拷 binlog 后落地的日志。还有慢查询日志，性能排查用。」

**[画面]** 四类日志卡片 + 各自用途标签。

**例子**
| 日志 | 层级 | 作用 |
| --- | --- | --- |
| redo log 重做日志 | InnoDB 存储引擎层 | 持久性、掉电/崩溃恢复 |
| undo log 回滚日志 | InnoDB 存储引擎层 | 原子性、事务回滚、MVCC |
| binlog 二进制日志 | Server 层 | 数据备份、主从复制 |
| relay log 中继日志 | 主从复制场景 | slave 拷贝 master 的 binlog 后落地 |

### 6.2 undo log：回滚的底气 (19:15 – 19:50)

**[画面]** 时间线动画：UPDATE 前 → 记录旧值到 undo → 执行更新 → 回滚时用旧值还原。

**口播**
「先看 undo log。事务提交前，MySQL 会把**更新前的数据**记进 undo log：插入时记主键，删除时记整条内容，更新时记旧值。回滚时做相反操作——删掉刚插入的，插回刚删除的，改回刚更新的。这就是原子性：要么全做，要么全不做。顺便说一句，MVCC 的数据版本链也是靠 undo log 串起来的。」

**[画面]** 三个小动画：INSERT 记主键 / DELETE 记内容 / UPDATE 记旧值。

### 6.3 redo log 与 WAL (19:50 – 20:50)

**[画面]** Buffer Pool 与磁盘之间，先写日志的流程图。

**口播**
「问题来了：有了 Buffer Pool 加速读写，但内存不可靠，断电就丢。于是有了 WAL——**写前日志**：更新时先改内存（标记脏页），同时把这次修改以 redo log 形式落盘，更新就算完成了；脏页等后台线程找时机再刷到磁盘。redo log 是**物理日志**，记录的是『哪个表空间、哪个数据页、哪个偏移量、改了什么』。」

**[画面]** 崩溃恢复动画：断电 → 重启 → 根据 redo log 重放 → 数据恢复。

**口播**
「为什么这样又安全又快？两个理由：第一，有了 redo log，即使数据库异常重启，已提交的记录也不会丢，这就是 **crash-safe** 能力；第二，redo log 是**追加写**，磁盘顺序写，而直接写数据要随机找位置、随机写——顺序写比随机写快得多。比喻一下：按顺序一页一页写笔记本，比写一个字还要翻到对应页快多了。」

**[画面]** 两个本子对比动画：左边流水账顺序写，右边翻来翻去随机写。

**口播**
「所以 redo log 一个东西解决两件事：**保持久性 + 把随机写变顺序写**。再对比一下 redo 和 undo：redo 记录更新**之后**的状态，undo 记录更新**之前**的状态；事务提交前崩溃用 undo 回滚，提交后崩溃用 redo 恢复。」

### 6.4 binlog 两阶段提交 (20:50 – 21:45)

**[画面]** 红绿灯动画：prepare → binlog → commit 三步走。

**口播**
「binlog 是 Server 层的日志，追加写、记录全量变更、不记录查询。问题来了：redo log 和 binlog 是两份独立日志，万一写了一半系统崩溃，两份日志就对不上了。MySQL 怎么保证一致？答案是**两阶段提交**，本质是内部 XA 事务：第一步 **prepare**——把 XID 写进 redo log，状态置为 prepare，落盘；第二步 **commit**——把 XID 写进 binlog 落盘，然后把 redo log 状态改成 commit。」

**[画面]** 崩溃恢复决策树动画。

**口播**
「崩溃恢复时，MySQL 扫描 redo log，凡是遇到 prepare 状态的事务，就拿 XID 去 binlog 里查：**binlog 里有这个 XID → 提交**（说明 binlog 已落盘，事务算成功）；**binlog 里没有 → 回滚**（binlog 还没写，redo 白写了）。所以两阶段提交的本质是：**以 binlog 写成功作为事务提交成功的标志**，哪份日志先写都不是，binlog 写完才算数。」

**[画面]** 决策树：prepare 状态 → 查 binlog 有 XID？→ 有=提交 / 没有=回滚。

### 6.5 一条 UPDATE 的完整旅程 (21:45 – 22:30)

**[画面]** 一张全景流程图，从上到下 8 个步骤动画依次点亮。

**口播**
「最后把前面所有知识串起来：一条 `UPDATE t_user SET name='xiaolin' WHERE id=1` 到底经历了什么？看这条流水线——」

**[画面]** 步骤条逐项点亮，每个步骤配图标。

**例子**
```
UPDATE t_user SET name='xiaolin' WHERE id=1 的完整流程：
① 执行器通过主键索引找到 id=1 这行（数据页在 Buffer Pool 就直接返回，
   不在就先从磁盘读入）
② 比较更新前后记录：一样 → 直接结束；不一样 → 进入更新流程
③ 开启事务，先写 undo log（记下旧值），undo 页的修改也要写 redo log
④ InnoDB 更新内存记录（标记脏页），把修改写进 redo log —— 到此更新完成
   （脏页不立即落盘，后台线程择机刷盘，这就是 WAL）
⑤ 记录 binlog，先写进 binlog cache，不落盘
⑥ 事务提交：两阶段提交
   prepare 阶段 → 把 redo log 状态置为 prepare 并刷盘
   commit 阶段 → binlog 刷盘，然后 redo log 状态置为 commit
⑦ 一条更新语句执行完成
```

**口播**
「记住关键节点：**先 undo 后 redo，先 redo 后 binlog，binlog 落盘才算提交成功**。这三句话能让你答出 80% 的日志相关面试题。」

## 第七章 性能调优 (22:30 – 25:30)

### 7.1 EXPLAIN 执行计划 (22:30 – 24:00)

**[画面]** 终端输入 `EXPLAIN SELECT * FROM user WHERE id=100;`，返回执行计划表。

**口播**
「面试官最后爱问：给你一张慢查询的表，你怎么排查？第一步永远是 **EXPLAIN**——在 SQL 前面加 EXPLAIN，看执行计划。重点看几个字段：`possible_keys` 可能用到的索引；`key` 实际用的索引，**如果 key 是 NULL 说明没走索引**；`key_len` 索引长度；`rows` 预计扫描行数；最重要的是 `type`，它描述扫描方式，效率从高到低是……」

**[画面]** 一个金字塔动画，从顶到底依次展示 type 类型。

**例子**
```
type 扫描方式效率从高到低：
const     → 主键或唯一索引 + 常量比较（如 id=1），最快
eq_ref    → 多表联查时，被驱动表用主键/唯一索引匹配
ref       → 非唯一索引扫描，可能返回多条
range     → 索引范围扫描（<、>、IN、BETWEEN）
index     → 全索引扫描（不用排序但开销大）
ALL       → 全表扫描，最坏情况，要尽量避免
```

**口播**
「记法：**const 最快，ALL 最慢**，写 SQL 的目标就是让 type 至少到 range 这一档以上。比如 `EXPLAIN SELECT * FROM user WHERE name='张三'`，如果 name 建了普通索引，type 是 ref、key 显示索引名，说明走索引了；如果 key 是 NULL，就要怀疑是不是索引选择性太差，或者用了函数导致索引失效。」

### 7.2 慢查询六大优化手段 (24:00 – 25:30)

**[画面]** 六张方案卡片依次弹出，每张配一个图标。

**口播**
「回到开头那个把系统拖死的慢查询，完整优化方案有六板斧——」

**[画面]** 卡片逐个点亮并配简短示例。

**例子**
```
① 分析查询：EXPLAIN 找出全表扫描、索引未利用的原因
② 创建/优化索引：WHERE、ORDER BY、JOIN、GROUP BY 的字段建索引；
   多字段建联合索引，且符合最左匹配
③ 避免索引失效：不左模糊、不对索引列用函数和表达式计算
④ 查询优化：不用 SELECT *，只取需要的列；能用覆盖索引就用；
   联表查询小表驱动大表，被驱动表字段要有索引；最好冗余字段避免联表
⑤ 分页优化：深分页把 LIMIT 转成按位置查询
   SELECT * FROM tb_sku WHERE id > 20000 LIMIT 10;
   （适用于主键自增的表）
⑥ 表设计优化：单表超千万考虑拆表；字段多的表按访问频率拆分；
   引入缓存层（Redis）存热点数据——读走旁路缓存，写先更新 DB 再删缓存
```

**口播**
「六板斧记不住？记住一条主线：**先 EXPLAIN 定位，再建索引，然后别让索引失效，最后从表结构和缓存下手**。大部分慢查询，死在前三招就能解决。」

## 附录：关键术语英文对照表

| 中文术语 | English Term | 含义说明 |
| --- | --- | --- |
| 索引 | Index | 加速查询的数据结构 |
| B+树 | B+ Tree | InnoDB 索引底层数据结构 |
| 聚簇索引 | Clustered Index | 叶子节点存放完整数据行的索引（主键索引） |
| 二级索引 / 辅助索引 | Secondary Index | 叶子节点存放「索引列 + 主键值」的索引 |
| 覆盖索引 | Covering Index | 查询字段全部在索引中，无需回表 |
| 回表 | Table Lookup (Back to Table) | 二级索引查到主键后，再回主键索引取完整记录 |
| 联合索引 | Composite Index | 多个字段组合的索引 |
| 最左匹配原则 | Leftmost Prefix Rule | 联合索引必须从最左列开始匹配才生效 |
| 前缀索引 | Prefix Index | 对字符字段前几个字符建立的索引 |
| 索引失效 | Index Invalidation | 查询条件导致无法使用索引 |
| 索引下推 | Index Condition Pushdown (ICP) | 优化器把条件判断下推到索引层（面试进阶） |
| 叶子节点 | Leaf Node | B+树最底层、存放数据的节点 |
| 非叶子节点 | Non-leaf Node | 只存键值和指针的导航节点 |
| 数据页 | Data Page | InnoDB 磁盘读写的最小单位 |
| 页目录 | Page Directory | 数据页内用于二分定位记录的槽结构 |
| 槽 | Slot | 页目录中指向每组最大记录的指针 |
| 事务 | Transaction | 一组原子性操作的集合 |
| 原子性 | Atomicity | 事务要么全做，要么全不做 |
| 一致性 | Consistency | 事务执行前后数据保持正确状态 |
| 隔离性 | Isolation | 并发事务互不干扰 |
| 持久性 | Durability | 提交后数据不丢失 |
| 脏读 | Dirty Read | 读到其他事务未提交的数据 |
| 不可重复读 | Non-repeatable Read | 事务内两次读同一行，值不同 |
| 幻读 | Phantom Read | 事务内两次查询，记录条数不同 |
| 隔离级别 | Isolation Level | 控制事务间隔离程度的配置 |
| 读未提交 | Read Uncommitted | 可读到未提交数据（最松） |
| 读已提交 | Read Committed | 提交后才可见 |
| 可重复读 | Repeatable Read | 事务内看到的数据与启动时一致（InnoDB 默认） |
| 串行化 | Serializable | 读写冲突排队执行（最严） |
| 多版本并发控制 | MVCC (Multi-Version Concurrency Control) | 通过多版本实现非阻塞读 |
| 读视图 | Read View | MVCC 中决定「看到哪个版本」的快照 |
| 活跃事务 | Active Transaction | 已启动但未提交的事务 |
| 锁 | Lock | 并发控制机制 |
| 全局锁 | Global Lock | 锁整个数据库（如备份时） |
| 表级锁 | Table-level Lock | 锁整张表 |
| 行级锁 | Row-level Lock | 锁单行记录（InnoDB 支持） |
| 记录锁 | Record Lock | 锁住已存在的一条记录 |
| 间隙锁 | Gap Lock | 锁住记录之间的区间，防止插入（防幻读） |
| 临键锁 | Next-Key Lock | 记录锁 + 间隙锁，左开右闭区间 |
| 意向锁 | Intention Lock | 快速判断表中是否有记录被加锁 |
| 元数据锁 | Metadata Lock (MDL) | 防止查询期间表结构被修改 |
| 共享锁 / 排他锁 | Shared Lock (S) / Exclusive Lock (X) | 读写锁，S 兼容 S，S 与 X 互斥 |
| 存储引擎 | Storage Engine | 管理数据存取、索引、事务的组件 |
| 重做日志 | Redo Log | 记录更新后状态，崩溃恢复用（持久性） |
| 回滚日志 | Undo Log | 记录更新前状态，回滚和 MVCC 用（原子性） |
| 二进制日志 | Binary Log (Binlog) | Server 层日志，备份和主从复制用 |
| 中继日志 | Relay Log | 从库接收主库 binlog 后生成的日志 |
| 慢查询日志 | Slow Query Log | 记录执行超时的 SQL |
| 两阶段提交 | Two-Phase Commit | 保证 redo log 与 binlog 一致 |
| 写前日志 | WAL (Write-Ahead Logging) | 先写日志、后落数据的策略 |
| 崩溃恢复 | Crash Recovery / Crash-safe | 异常重启后数据不丢的能力 |
| 脏页 | Dirty Page | 内存中已修改但未落盘的数据页 |
| 缓冲池 | Buffer Pool | InnoDB 内存缓存区 |
| 执行计划 | Execution Plan | EXPLAIN 输出的 SQL 执行方案 |
| 全表扫描 | Full Table Scan | 不走索引，扫整张表（type=ALL） |
| 全索引扫描 | Index Scan | 扫整个索引（type=index） |
| 索引范围扫描 | Range Scan | 走索引的范围查找（type=range） |
| 主从复制 | Master-Slave Replication | 主库 binlog 同步到从库的机制 |
| 页级锁 | Page-level Lock | 已移除的 BDB 引擎特性，InnoDB/MyISAM 无 |
| 共享表空间 | Shared Tablespace (ibdata1) | 多个表共用数据文件（旧默认） |
| 独占表空间 | Per-table Tablespace (.ibd) | 每表独立数据文件（5.6.6 后默认） |
| 外键约束 | Foreign Key Constraint | InnoDB 支持的数据完整性约束 |
