## 第一章 数据结构底层实现 (0:40 – 6:30)

### 1.1 九种数据类型与场景 (0:40 – 1:30)

**[画面]** 九张类型卡片逐个弹出，每张配一个小图标。

**口播**
「先看全景。Redis 常见五种类型：String、Hash、List、Set、Zset，加上后面新增的 BitMap、HyperLogLog、GEO、Stream，一共九种。面试最常考的是『某种类型的应用场景』，我直接给结论——」

**[画面]** 场景表格逐行点亮。

**例子**
```
五种基本类型：
String → 缓存对象、计数器、分布式锁、共享 session
List   → 消息队列（但生产者要自己实现全局唯一 ID，且不能消费组消费）
Hash   → 缓存对象、购物车
Set    → 聚合计算：点赞、共同关注、抽奖（交集/并集/差集）
Zset   → 排序场景：排行榜、电话簿按姓名排序

四种扩展类型：
BitMap      → 签到、用户登录状态、连续签到统计（二值状态统计）
HyperLogLog → 百万级网页 UV 计数（海量基数统计）
GEO         → 滴滴叫车（地理位置）
Stream      → 消息队列（自动生成全局唯一消息 ID，支持消费组）
```

**口播**
「Zset 是面试宠儿，先记住一个真实用法：排行榜。小林发了五篇博文，赞数是 200、40、100、50、150。加赞用 `ZINCRBY`，查赞数用 `ZSCORE`，查前 3 名用 `ZREVRANGE`，查 100 到 200 赞的用 `ZRANGEBYSCORE`——一个排行榜就这么立起来了。」

**[画面]** 终端演示四条命令逐条执行，排行榜动画实时变化。

### 1.2 Set vs ZSet 的区别 (1:30 – 2:00)

**[画面]** 左右分屏：左边 Set 无序球体，右边 ZSet 有序阶梯。

**口播**
「Set 和 ZSet 就差一个『Z』，但能力差一个维度：Set 是无序去重集合，只能做元素本身的交并差；ZSet 每个元素带一个分数 score，按分数排序，所以多了排序、范围查询、排名计算这些基于分数的操作。总结一句：**Set 管『有没有』，ZSet 管『排第几』**。」

**[画面]** 命令对比表格。

**例子**
```
Set：  SADD / SMEMBERS / SISMEMBER / SINTER / SUNION
ZSet： ZADD key 10 "a" / ZRANGE key 0 -1 WITHSCORES
       ZRANGEBYSCORE key 12 25 / ZINCRBY key 5 "a" / ZRANK key "b"
```

### 1.3 String 为什么用 SDS (2:00 – 2:50)

**[画面]** C 字符串与 SDS 结构对比图，四个字段高亮。

**口播**
「String 的底层不是 C 语言字符串，而是 SDS——简单动态字符串。C 字符串有三个缺陷：取长度要遍历、不能存二进制、容易缓冲区溢出。SDS 在字符数组之上加了三个元数据：`len` 记录长度、`alloc` 记录分配空间、`flags` 区分类型，后面才是数据 `buf[]`。」

**[画面]** 三个缺陷的对比动画：strlen 遍历 vs 直接返回 len；遇到 \0 截断 vs 按 len 取；strcat 溢出 vs alloc-len 自动扩容。

**例子**
```
SDS 结构：len | alloc | flags | buf[]
① O(1) 获取长度    —— C 语言 strlen 要遍历 O(N)
② 二进制安全       —— 不用 \0 结尾标识，可存任意二进制（结尾仍加 \0 兼容 C 库函数）
③ 防缓冲区溢出     —— 修改前先算 alloc-len，不够自动扩容
```

**口播**
「这三个字段，就是面试官最爱追问的三个点：O(1) 取长度、二进制安全、防缓冲区溢出。背下来。」

### 1.4 跳表：Zset 的加速器 (2:50 – 4:10)

**[画面]** 三层跳表动画：L0 五个节点、L1 三个节点、L2 一个节点，高亮查找节点 4 的跳跃路径。

**口播**
「Zset 元素多时底层用跳表。普通链表查找是 O(N)——查节点 4 要逐个走 4 次。跳表在链表上叠了『多层』：假设 L0 层有节点 1~5，L1 层有节点 2、3、5，L2 层只有节点 3。查找节点 4 时，从头节点直接走 L2 跳到节点 3，再往前一格就到 4——只需要 2 次。数据量大时，跳表查找是 O(logN)。」

**[画面]** 跳表节点结构展开：ele（元素）、score（分数）、backward（后向指针）、level[] 数组（每层 forward 指针 + span 跨度）。

**口播**
「跳表节点怎么实现多层？每个节点有 `level[]` 数组，一个元素代表一层；每层存指向下一个节点的指针和跨度 span。节点还有个 `backward` 后向指针方便倒序遍历。层高怎么定的？**掷骰子**——创建节点时生成 [0,1) 随机数，小于 0.25 就加一层继续掷，直到大于 0.25 停止，层高最大 64。所以跳表并没有严格维持 2:1 的层数比例，靠概率保证平均性能。」

**[画面]** 掷骰子动画：0.25 概率加层，掷出 0.18 → 加层，掷出 0.52 → 停止。

### 1.5 为什么用跳表不用 B+ 树 (4:10 – 4:55)

**[画面]** 跳表和 B+ 树左右对垒，头顶标着「内存」和「磁盘」。

**口播**
「面试高频题：MySQL 用 B+ 树，Redis 为什么用跳表？核心一句话：**场景不同**。B+ 树是为磁盘设计的——压缩树高、减少磁盘 I/O 次数，但代价是插入删除要处理节点分裂合并，代码复杂、写操作可能抖动。Redis 是纯内存操作，没有磁盘 I/O 瓶颈，多跳几次指针开销极小，而跳表插入删除只改局部指针，几十到几百行 C 代码就实现，性能同样是 O(logN)。」

**[画面]** 对比表格逐行点亮。

**例子**
| 特性 | 跳表 Skip List | B+ 树 |
| --- | --- | --- |
| 主要场景 | 内存数据库（Redis） | 磁盘数据库（MySQL） |
| 查找复杂度 | 平均 O(logN) | O(logN)，树更矮 |
| 实现难度 | 低，几百行 C 代码 | 高，要处理分裂、合并 |
| 写操作代价 | 局部指针修改，无全局重平衡 | 可能引发连锁分裂/合并 |
| 结论 | 内存场景最优解 | 磁盘场景最优解 |

**口播**
「所以这不是谁更先进的问题，是适配场景——B+ 树是磁盘场景最优解，跳表是内存有序数据场景最优解。」

### 1.6 压缩列表与连锁更新 (4:55 – 5:45)

**[画面]** 压缩列表结构图：头四字段 + 一串 entry 节点。

**口播**
「Zset 元素少时（小于 128 个且每个小于 64 字节）用压缩列表，它是连续内存块组成的顺序结构，为了省内存。表头四个字段：`zlbytes` 总字节数、`zltail` 尾节点偏移量、`zllen` 节点数量、`zlend` 结束标记 0xFF。靠 zltail 和 zllen，找第一个和最后一个元素是 O(1)。每个节点包含 `prevlen`（前一个节点的长度）、`encoding`（数据类型和长度）、`data`（实际数据）。」

**[画面]** 连锁更新动画：中间一个节点变大 → 后面节点的 prevlen 空间不够 → 连环扩容。

**口播**
「压缩列表的致命缺点是**连锁更新**：每个节点都存前一个节点的长度，一旦某个节点变大，后面节点的 prevlen 字段就要扩容，扩容又影响更后面的节点……像多米诺骨牌一样连锁反应，导致内存多次重新分配。所以压缩列表只适合节点少的场景。Redis 后来设计了 quicklist（3.2）和 listpack（5.0）来彻底解决它。」

### 1.7 listpack：没有 prevlen 的下一代 (5:45 – 6:10)

**[画面]** listpack 结构图：头（总字节数+元素数量）+ entry 节点，节点只有 encoding/data/len 三部分。

**口播**
「listpack 是压缩列表的接班人，最大区别：**节点里不再保存前一个节点的长度**，只记录当前节点的长度。这样插入新元素不会影响其他节点的长度字段，连锁更新从根上被消灭。Redis 7.0 里压缩列表正式废弃，由 listpack 接管。」

### 1.8 哈希表扩容与渐进式 rehash (6:10 – 6:30)

**[画面]** 两张哈希表动画：表 1 装满了，表 2 被分配两倍空间，数据逐步迁移。

**口播**
「最后是哈希表扩容。Hash 类型的底层是哈希表，数据多了要 rehash：先给哈希表 2 分配两倍空间，把表 1 的数据迁过去，完了释放表 1、表 2 转正。问题来了：如果数据几百万条，一次性迁移会阻塞 Redis。所以用**渐进式 rehash**——把迁移拆散，每处理一个请求就顺带迁移一小批，增删改查同时查两张表，新写入只进表 2。这样大迁移的开销被摊平到每次请求里，Redis 永远不卡。」

**[画面]** 拆分动画：一次性大箭头变成多个小箭头，标注「开销摊平」。

## 第二章 线程模型 (6:30 – 9:00)

### 2.1 Redis 为什么快 (6:30 – 7:10)

**[画面]** 三个原因卡片：内存、单线程、I/O 多路复用。

**口播**
「面试第一问：Redis 为什么快？三个原因。第一，大部分操作在内存完成，还用了高效数据结构，瓶颈是内存和网络带宽而不是 CPU——CPU 不是瓶颈，就没必要上多线程。第二，单线程避免了线程竞争、上下文切换和死锁。第三，**I/O 多路复用**：一个线程同时监控大量客户端连接，内核里同时监听多个 Socket，谁有数据就处理谁，不用挨个等。官方基准测试，单线程 Redis 吞吐量能到 10W QPS。」

**[画面]** 数字跳动动画：QPS 飙到 100,000。

### 2.2 单线程的真相：后台线程与 6.0 多线程 (7:10 – 8:00)

**[画面]** 线程组成图：主线程 + 三个 BIO 线程，标注各自职责。

**口播**
「说 Redis 是单线程，指的是『接收请求→解析→执行命令→返回』这条主链路是单线程。但 Redis 程序本身是**多线程的**：启动时会拉 3 个后台线程，分别处理关闭文件、AOF 刷盘、异步释放内存（lazyfree）。重点来了——删除大 Key 千万别用 DEL，DEL 在主线程执行，会卡住整个 Redis；要用 `UNLINK` 异步删除，把活儿丢给后台线程。Redis 6.0 之后又加了 I/O 多线程处理网络读写，但**命令执行仍然是单线程**，别误解成命令并行执行。而且这个特性默认关闭，要手动配 `io-threads` 才开。」

**[画面]** 大 Key 删除对比动画：DEL 卡住主线程 vs UNLINK 后台异步。

**例子**
```
主线程：Redis-server，执行命令和网络 I/O
BIO 后台线程（3 个）：
  bio_close_file  → 关闭文件
  bio_aof_fsync   → AOF 刷盘
  bio_lazy_free   → 异步释放内存（UNLINK / FLUSHDB ASYNC）

6.0 新增：io-threads N → 额外 N-1 个 I/O 线程处理网络读写（默认关闭）
```

### 2.3 I/O 多路复用与网络模型 (8:00 – 9:00)

**[画面]** 事件循环动画：多个客户端 FD 注册到 epoll，就绪事件被分发给处理器。

**口播**
「I/O 多路复用怎么理解？『多路』指多个网络连接，『复用』指复用同一个线程。Redis 用 epoll 等机制把所有客户端 Socket 的文件描述符注册进去，内核同时监听它们；一旦某个 Socket 有数据，事件处理器立刻回调处理，不会傻等某个客户端。整个模型是 Reactor 模式：6.0 之前是单 Reactor 单线程——简单、无竞争，但用不满多核 CPU；6.0 之后网络 I/O 变成多线程 Reactor，命令执行保持单线程。一句话总结：**单线程执行命令，多线程搬运网络数据**。」

**[画面]** 单 Reactor 单线程 vs 多 Reactor 多线程架构对比图。

## 第三章 持久化 (9:00 – 11:30)

### 3.1 三种持久化方式全景 (9:00 – 9:30)

**[画面]** 三张卡片：AOF、RDB、混合持久化，各自配示意图。

**口播**
「Redis 数据在内存，重启就丢，所以要有持久化。一共有三种：**AOF**——每执行一条写命令就追加记到文件里，像记账本；**RDB**——某一瞬间的内存数据拍成二进制快照，像照片；**混合持久化**——Redis 4.0 新增，AOF 重写时先写 RDB 格式再追加 AOF 命令，恢复快而且丢得少。我们一个一个讲。」

### 3.2 AOF：追加命令日志 (9:30 – 10:15)

**[画面]** 终端：执行 `set name xiaolin`，AOF 文件里出现对应记录。

**口播**
「AOF 的实现：执行完写命令，把命令追加到 aof_buf 缓冲区，事件循环结束前 write 到内核 page cache，最后靠 fsync 决定什么时候真正落盘。三种策略由 `appendfsync` 配置——」

**[画面]** 三策略对比表 + 时钟动画表示 everysec 每秒刷一次。

**例子**
```
appendfsync 三种策略：
Always   → 每条写命令都立刻 fsync 落盘：最安全，性能最差
Everysec → 每 1 秒后台刷一次盘：最多丢 1 秒数据（默认，性价比之选）
No       → 不主动 fsync，交给操作系统：性能最好，丢失不可控
```

**口播**
「记忆口诀：**Always 不丢但慢，Everysec 一秒一丢是默认，No 全看操作系统心情**。」

### 3.3 RDB：内存快照 (10:15 – 11:00)

**[画面]** 相机拍照动画 + save/bgsave 对比。

**口播**
「AOF 记录的是命令，恢复时要重放所有命令，日志一多恢复就慢。RDB 直接记录某一瞬间的内存数据——恢复时把文件读进内存就行，快得多。生成 RDB 有两个命令：`SAVE` 在主线程生成，会阻塞 Redis；`BGSAVE` 派子进程生成，不阻塞主线程——生产环境用 bgsave。RDB 的代价是两次快照之间崩溃会丢数据，而且快照本身也耗性能，所以一般两者配合用。」

**[画面]** 优缺点天平对比。

**例子**
```
AOF 优点：默认最多丢 1 秒数据，安全性高；支持多种同步策略；
          可重写瘦身；损坏可用 redis-check-aof 修复
AOF 缺点：文件大；always 时写性能下降；恢复要重放全部命令，慢

RDB 优点：快照文件小，备份恢复快；bgsave 不阻塞主线程
RDB 缺点：两次快照之间崩溃会丢数据；快照期间有写操作，恢复后可能与故障前不完全一致
```

### 3.4 混合持久化 (11:00 – 11:30)

**[画面]** 混合文件结构图：前半段 RDB 二进制 + 后半段 AOF 命令。

**口播**
「Redis 4.0 的混合持久化是把两个优点缝在一起：开启 `aof-use-rdb-preamble yes` 后，AOF 重写时**先用 RDB 格式写入当前内存状态，再把重写期间新收到的命令以 AOF 形式追加在后面**。重启恢复时先快速加载 RDB 部分，再回放少量 AOF 命令——RDB 的恢复速度、AOF 的低丢失率，两个都要。」

## 第四章 过期删除与内存淘汰 (11:30 – 13:00)

### 4.1 两个容易混的概念 (11:30 – 11:50)

**[画面]** 左右对比：左边「内存满了」，右边「键过期了」。

**口播**
「先分清两个概念：**内存淘汰**是内存满了，主动腾地方；**过期删除**是把已经过期的键清掉。一个是空间问题，一个是时间问题，别混。」

### 4.2 过期删除：惰性删除 + 定期删除 (11:50 – 12:30)

**[画面]** 两个机制动画：惰性删除（访问时检查）和定期删除（定时抽查）。

**口播**
「Redis 的过期键不立即删，而是『惰性删除 + 定期删除』组合。**惰性删除**：访问或修改 key 前先检查，过期就删，不访问就永远躺着。**定期删除**：每秒 10 次（hz 配置，默认 10），每轮从过期字典**随机抽 20 个 key** 检查；如果过期比例超过 25%（超过 5 个），就再抽一轮，直到比例低于 25%，整轮最长 25 毫秒就强制停。」

**[画面]** 抽签动画：20 个 key 抽出，过期超过 5 个就继续抽。

**例子**
```
定期删除参数（源码写死）：
- 每秒检查次数：hz 10（可配置）
- 每轮抽查：随机 20 个 key
- 续抽条件：过期 key 占比 > 25%（20/4 = 5 个）
- 单轮时间上限：25 ms，防止卡死
```

**口播**
「为什么不过期立即删？因为过期 key 多时，立刻删除会占用大量 CPU 时间，而内存又不紧张——把 CPU 花在删和当前任务无关的键上，会拖慢响应。所以 Redis 选择抽查懒删，在 CPU 时间和内存浪费之间找平衡。」

### 4.3 八种内存淘汰策略 (12:30 – 13:00)

**[画面]** 策略树状图：两大分支「不淘汰」和「淘汰」，再分「只淘汰过期键」和「全键」。

**口播**
「内存淘汰策略一共八种，两条主线。默认是 `noeviction`：内存满了直接拒绝写入、报错但不淘汰任何数据。剩下七种分两类：在**设置了过期时间的键**里淘汰——random 随机、ttl 优先淘汰最早过期的、lru 淘汰最久未使用、lfu 淘汰最少使用；在**所有键**里淘汰——allkeys-random、allkeys-lru、allkeys-lfu。生产常用 allkeys-lru 或 allkeys-lfu，热点数据天然留下。」

**[画面]** 策略表格逐行点亮，lru/lfu 图标区分。

**例子**
```
不淘汰：      noeviction（默认）：满了报错，不淘汰
过期键里淘汰：volatile-random / volatile-ttl / volatile-lru / volatile-lfu
全部键里淘汰：allkeys-random / allkeys-lru / allkeys-lfu（4.0 新增 lfu 系列）
```

## 第五章 集群 (13:00 – 16:30)

### 5.1 主从同步：全量 + 增量 (13:00 – 14:10)

**[画面]** 主从两节点动画，先全量后增量的时间线。

**口播**
「单机 Redis 挂了就没了，于是有主从架构。主从第一次同步是全量同步，分三阶段：从库发 `SYNC` 命令；主库生成 RDB 快照发给从库，**生成和传输期间的新写命令先记到 replication backlog 缓冲区**；RDB 传完，主库再把这些缓冲命令补发给从库。三阶段走完，主从一致。」

**[画面]** 三阶段流程动画：SYNC → RDB 传输（同时缓冲新命令）→ 补发缓冲命令。

**口播**
「断线重连就不必再全量了，用增量同步：从库发 `PSYNC` 命令带上自己的复制偏移量，主库一看偏移量，检查自己的 `repl_backlog_buffer`——**这是个环形缓冲区，默认 1M**——如果从库要读的数据还在里面，就用增量同步，把断线期间的命令补发过去；如果已经被环形缓冲区覆盖了，只能退回全量同步。所以这个缓冲区要尽量调大，否则主库写太快、从库读太慢，一覆盖就频繁全量同步，性能损耗很大。」

**[画面]** 环形缓冲区动画：写指针追上读指针，数据被覆盖 → 红色警告「触发全量同步」。

**例子**
```
全量同步（初次连接/数据丢失/差异过大）：
① 从库发 SYNC
② 主库生成 RDB 发送；期间新命令写入 repl_backlog_buffer
③ RDB 传完后补发缓冲中的命令

增量同步（断线重连）：
① 从库发 PSYNC（带自己的 slave_repl_offset）
② 主库比对 master_repl_offset，若差异数据还在环形缓冲区 → 增量
③ 若已被覆盖 → 退回全量同步
```

### 5.2 主从能保证一致性吗 (14:10 – 14:30)

**[画面]** CAP 三角形图，Redis 落在 AP 角。

**口播**
「主从和集群能保证强一致吗？不能。Redis 在 CAP 理论里属于 **AP 模型**——网络分区时优先保证可用性和分区容错，牺牲强一致性。也就是说分区期间集群照常服务，但不同节点之间数据可能不一致。记住这句话，面试里问『主从怎么保证一致性』的陷阱题就破了。」

### 5.3 哨兵机制 (14:30 – 15:30)

**[画面]** 哨兵节点环绕主从节点，眼睛图标扫描。

**口播**
「主库挂了怎么办？人工切换太慢，所以 Redis 2.8 之后有哨兵 Sentinel——一个特殊模式的 Redis 进程，干三件事：**监控、选主、通知**。挂掉判定分两步：每个哨兵定时发心跳，主节点超过 down-after-milliseconds 没回应，被这个哨兵判**主观下线**；但一家之言不算数，该哨兵去问其他哨兵，超过 quorum 数量的哨兵都认为它挂了，才判**客观下线**，开始故障转移。」

**[画面]** 四步流程动画：主观下线 → 客观下线 → 选哨兵 Leader → 选新主节点。

**口播**
「然后哨兵集群先要选出一个哨兵 Leader：每个哨兵都能竞选，拉票超过『max(quorum, 哨兵数/2+1)』就当选。比如 3 个哨兵、quorum 为 2，拿到 2 票就胜出。哨兵 Leader 再从从节点里挑新主节点，按优先级依次看：先过滤故障节点，选 `slave-priority` 最高的；没有就选复制偏移量最大的（数据最全）；再没有就选 runid 最小的。三步过滤完，新主上位，哨兵通知所有从节点和客户端。」

**例子**
```
选新主节点三步：
① 过滤故障节点
② 选 slave-priority 最大
③ 选复制偏移量最大（数据最全）
④ 选 runid 最小
```

### 5.4 切片集群：16384 个哈希槽 (15:30 – 16:30)

**[画面]** 数据 → CRC16 计算 → 取模 16384 → 槽 → 节点，漏斗式动画。

**口播**
「数据量大到一台机器装不下，就要切片集群 Redis Cluster。它把数据分到 16384 个哈希槽里：每个 key 先按 **CRC16 算法**算出一个 16 bit 值，再对 16384 取模，得到 0~16383 的槽号。槽怎么分给节点？`cluster create` 自动平均分配，或者用 `cluster addslots` 手动分配——注意手动分配必须把 16384 个槽全部分完，集群才能正常工作。」

**[画面]** 客户端寻址动画：本地缓存槽位映射表 → 算槽号 → 查表 → 直连节点；槽位变动时收到 MOVED/ASK。

**口播**
「客户端怎么知道访问哪个节点？启动时向任意节点发 `CLUSTER SLOTS` 拿到全量『槽位-节点』映射并缓存。访问 key 时先算槽号再查缓存直连。节点变动时，会收到 **MOVED**（永久迁移，更新缓存）或 **ASK**（临时迁移）重定向指令，客户端自动更新映射——这就是透明分片。集群的优点：高可用、好扩展、性能随节点数涨；缺点：部署运维复杂、跨节点操作受限、数据同步有延迟。」

**[画面]** 集群优缺点卡片。

**例子**
```
key 映射到节点：
key → CRC16(key) → 16 bit 值 → 对 16384 取模 → 槽号（0~16383）→ 节点

槽分配：
平均分配：cluster create 自动均分
手动分配：cluster meet + cluster addslots（必须分完 16384 个槽）
客户端：CLUSTER SLOTS 拿映射 → 本地缓存 → 算槽查表直连 → MOVED/ASK 更新
```

## 第六章 缓存三大问题与一致性 (16:30 – 19:30)

### 6.1 雪崩、击穿、穿透 (16:30 – 17:40)

**[画面]** 三个场景动画对比，瀑布、锤子、钻头图标区分。

**口播**
「回到开场那个事故。缓存三大问题，一字之差，别搞混——」

**[画面]** 每个问题配独立动画：雪崩（一大片缓存同时熄灭）、击穿（一个热点熄灭）、穿透（请求绕开缓存直钻数据库）。

**口播**
「**雪崩**：大量缓存同一时间过期，或者 Redis 直接宕机，所有请求瞬间打到数据库。**击穿**：单个热点 key 过期，刚好大量请求访问它，数据库被冲垮——区别是『一批』和『一个』。**穿透**：请求的数据缓存和数据库里**都不存在**，缓存永远建不起来，恶意刷这种请求，数据库被白打。」

**[画面]** 解决方案表格逐行点亮。

**例子**
```
缓存雪崩（大面积过期/宕机）：
① 过期时间加随机数，避免同一时刻集体过期
② 互斥锁：同一时间只允许一个请求重建缓存
③ 后台线程定时更新缓存，不设过期时间

缓存击穿（单个热点过期）：
① 互斥锁
② 热点数据不设过期时间，后台异步更新；或快过期前提前刷新

缓存穿透（数据不存在）：
① 请求入口校验非法参数，直接拦截
② 缓存空值/默认值
③ 布隆过滤器：快速判断数据是否存在，不存在就不查数据库
```

**口播**
「记住三个关键词：雪崩是『一片』，击穿是『一个热点』，穿透是『不存在』。对应解法里，互斥锁、空值缓存、布隆过滤器是三大主力。」

### 6.2 布隆过滤器原理 (17:40 – 18:20)

**[画面]** 8 位位图数组 + 3 个哈希函数动画。

**口播**
「布隆过滤器是解决穿透的核心，原理很简单：一个初始全 0 的位图数组 + N 个哈希函数。写入数据 x 时，用 3 个哈希函数算出 3 个哈希值，对数组长度取模，假设得到 1、4、6，就把这三位全部置 1。查询 x 时同样算三位，**只要有一位是 0，就说明 x 一定不存在**，直接拦截，不用查数据库。」

**[画面]** x 和 y 冲突动画：两个数据落在同一批位置上。

**口播**
「代价是**误判**：哈希冲突可能让 x 和 y 落在同一批位置，所以『说存在不一定存在，说不存在一定不存在』——布隆过滤器可以 100% 拦截不存在的 key，但可能把不存在的放进来。对拦截穿透来说，这个特性刚刚好。」

**例子**
```
位图数组长度 8，哈希函数 3 个：
写入 x：h1(x)%8=1, h2(x)%8=4, h3(x)%8=6 → 第 1、4、6 位置 1
查询 x：查第 1、4、6 位，全为 1 → 可能存在；任一为 0 → 一定不存在
```

### 6.3 缓存与数据库一致性 (18:20 – 19:30)

**[画面]** 读写两条路径动画：读走旁路缓存，写先更新 DB 再删缓存。

**口播**
「缓存和数据库怎么保持一致？读操作走**旁路缓存**：命中直接返回，不命中就从数据库加载再写回缓存。写操作是『**先更新数据库，再删除缓存**』。为什么先更新 DB 再删缓存而不是先更缓存？因为删缓存让下次读重新加载，比更新缓存更能避免并发下的脏数据。但要注意：缓存本质是牺牲强一致性换性能，属于 CAP 的 AP，只能追求最终一致。另外缓存一定要设过期时间——太短请求多落库失去意义，太长脏数据滞留还浪费内存。」

**[画面]** 两个兜底方案动画：消息队列重试、Canal 订阅 binlog。

**口播**
「删缓存失败怎么办？两个兜底方案：第一，**消息队列重试**——把删除操作放进队列，失败就重试，超过次数告警；第二，**订阅 binlog**——阿里开源的 Canal 把自己伪装成 MySQL 从节点，订阅 binlog 拿到变更数据，再触发删缓存，业务代码零侵入。写操作顺序反了也没关系，最终一致性能兜底。」

**例子**
```
读：Cache-Aside（旁路缓存）：先查缓存 → 未命中查 DB → 回填缓存
写：先更新 DB → 再删缓存

删缓存失败的兜底：
① 消息队列 + 重试机制（侵入业务代码）
② Canal 订阅 MySQL binlog → 触发删缓存（无侵入，推荐）
```

## 第七章 高并发实战场景 (19:30 – 23:00)

### 7.1 Redis 的原子性与分布式锁 (19:30 – 20:40)

**[画面]** 分布式锁时序图：三个客户端抢锁，只有一方成功。

**口播**
「Redis 单命令是原子的——单线程执行，天然无竞争。但多条命令的原子性要靠 **Lua 脚本**：Redis 把整个 Lua 脚本当整体执行，中间不会被其他命令打断。经典应用是分布式锁：加锁用 `SET lock_key unique_value NX PX 10000`，NX 保证 key 不存在才设置、PX 设置 10 秒过期防止客户端崩了锁不释放、unique_value 标识客户端防止误删别人的锁。解锁是两个操作——先判断锁是不是自己的，是才删除，必须用 Lua 保证原子性。」

**[画面]** 加锁/解锁命令动画，Lua 脚本高亮。

**例子**
```
加锁：SET lock_key unique_value NX PX 10000
      NX = key 不存在才设置（抢锁）
      PX 10000 = 10 秒过期（防死锁）
      unique_value = 客户端唯一标识（防误删）

解锁（两个操作，必须 Lua 保证原子性）：
if redis.call("get", KEYS[1]) == ARGV[1]
then redis.call("del", KEYS[1]) end
```

**口播**
「单节点锁够用；跨多个独立 Redis 实例的强可靠性方案是作者提出的 **RedLock**——在多数实例（超过半数）上加锁成功才算拿锁，减少单点故障影响。另外提醒：Redis 的 MULTI/EXEC 事务能保证正常执行时全部完成，但**执行中出错不会回滚**——Redis 没有回滚机制，所以别把它当数据库事务用。」

### 7.2 大 Key 问题 (20:40 – 21:25)

**[画面]** 一个巨大的钥匙图标压垮服务器，五个危害卡片弹出。

**口播**
「大 Key 指某个 key 的 value 太大：字符串超过 1M，或集合类元素超过 1 万个，就算大 Key——具体阈值看业务，高并发低延迟场景 10KB 就可能算。它的危害有五个：内存占用高、性能下降、**阻塞其他操作**（DEL 一个大 key 会让 Redis 卡住几秒）、网络拥塞（1MB 的 key 每秒访问 1000 次就是 1000MB 流量）、主从同步延迟，集群下还会造成**数据倾斜**。」

**[画面]** 解决方案动画：拆分、清理、监控、定时清过期。

**口播**
「怎么解决？四招：**拆分**——几万成员的 Hash 拆成多个小 Hash；**清理**——不合适的挪到别的存储，删除要用异步删除（UNLINK）；**监控**——内存水位超 70% 或 1 小时增长超 20% 就报警；**定期清理过期数据**——堆积的过期数据也是大 Key 的来源。」

**例子**
```
大 Key 判定：字符串 value > 1M，或集合元素 > 1 万个（参考值，随业务浮动）
危害：内存高 / 性能降 / 阻塞 DEL / 网络拥塞 / 主从延迟 / 集群数据倾斜
解决：拆分 Hash → 异步清理 → 水位监控（70%/小时 20%）→ 定期清过期
```

### 7.3 热 Key 问题 (21:25 – 21:55)

**[画面]** 温度计动画：单个 key 的 QPS 占据总量 70%，温度爆表。

**口播**
「热 Key 是另一个极端——某个 key 被疯狂访问：实例总 QPS 1 万，它一个就占了 7000；或者每秒大量 HGETALL 一个上千成员的 Hash。单节点扛不住，怎么办？两招：**复制热 Key**——把 hot key 复制成 foo2、foo3、foo4 三个一模一样的 key 分散到不同分片；或者**读写分离**——加从节点分担读压力，但会增加架构复杂度。」

**[画面]** 热 key 复制动画：一个 key 变四个，分流到不同节点。

### 7.4 秒杀场景设计 (21:55 – 23:00)

**[画面]** 秒杀架构全景图：Redis 预减库存 → 异步队列 → 数据库落单。

**口播**
「压轴题：秒杀怎么扛住高并发还不超卖？面试官想要的完整链路是这样的——系统启动时把库存加载进 Redis；用户下单先用 `DECR` 原子预减库存，减到 0 直接返回失败；**只有减成功的请求**才进异步队列，先返回『排队中』；后端异步队列再判断用户是否重复秒杀，出队的请求才真正生成订单、扣数据库库存；用户轮询看结果。用 Redis 的原子性挡住 99% 的请求，数据库只扛真正成交的那几个——这就是秒杀的精髓。」

**[画面]** 五步流程动画逐帧展示，库存数字从 100 减到 0。

**口播**
「更高级的分段锁方案：100 件库存拆成 5 个 key，每个 20 件，用户 id 对 5 取模落到不同 key，5 个请求能并发处理——但要注意某段卖完要自动换段。至于数据库层面的 `SELECT ... FOR UPDATE` 排他锁，高并发下性能差、容易超时，一般只做兜底。」

**例子**
```
秒杀链路：
① 初始化：库存加载进 Redis（如 stock:100）
② 预减库存：DECR stock（原子操作），<=0 直接返回秒杀失败
③ 成功的请求进异步队列，返回「排队中」
④ 异步队列出队 → 校验重复秒杀 → 生成订单 → 扣数据库库存
⑤ 客户端轮询查询秒杀结果

进阶：分段库存 —— 100 库存分 5 个 key，user_id % 5 定位分片，并发处理
```
