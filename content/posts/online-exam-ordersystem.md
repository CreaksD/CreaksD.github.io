8 月 12 号，我经历了人生第一场全栈工程师的线上机试。

90 分钟，允许使用任何 AI 工具。系统里已经部署好 MySQL、Redis 和一个会持续推订单的 Docker 服务。我要做的，是写一个服务接收订单、处理订单、展示监控面板——然后打包上传。

最后的结果是：**我没做完**。

但这次没做完，比做完了收获更大。这篇文章把原题、我的方案和复盘记录下来，给以后的自己和正在准备机试的朋友。

## 原题：订单处理与监控系统

考试系统会持续调用我的接口推送订单，接口长这样：

```json
POST /api/orders/batch
{
  "push_batch": "PUSH-001",
  "orders": [
    {
      "order_id": "ORDER-000001",
      "order_time": "2026-08-02T10:20:30Z",
      "product_id": 10001,
      "quantity": 2,
      "unit_price": "19.90"
    }
  ]
}
```

要求拆开是四条：

1. 接收订单，按 `product_id` 查商品表**回填商品名**，写入 MySQL 订单表
2. 识别**重复订单**，避免重复入库和重复统计
3. 应用监听 `0.0.0.0:18080`，提供 `GET /health`
4. 一个监控页面：5 秒一个统计周期、最近 180 秒的接收/入库图表 + 最新 5 批数据 + TOP5 商品累计金额

系统只允许用 MySQL 和 Redis，架构自选。

还有一个**最要命的约束**藏在题目里：接口必须**在 2 秒内返回**，超时考试系统就直接放弃这次推送。后面你会发现，这条约束几乎决定了整个方案长什么样。

## 坑一：我花了大把时间连一个根本连不上的虚拟机

机试一开始，我以为系统给我开了一台虚拟机，可以用本地的 FinalShell 连上去操作。

于是：配主机、配账号、换端口、试各种连接方式……反复折腾了很久，全部失败。

最后才发现：**安全组把 SSH 端口关了**。真实的交付方式是打开浏览器里的**网页终端**，把打包好的 zip 拖拽上传，他们用 Docker 环境跑起来。我浪费掉的时间，几乎全耗在这个误判上。

> 复盘教训：动手写代码之前，先花五分钟搞清楚**交付环境**——怎么提交、怎么运行、有没有大小限制、环境里有什么。这一步永远不要跳过。

## 坑二：没注意 10MB 限制，30 多 MB 的包直接打回

搞清楚交付方式后，我又踩了第二个坑。

题目要求 zip 包**小于 10MB**。我第一反应是"能打包就行"，直接用了熟悉的框架打 jar——结果 jar **30 多 MB**，压缩后远远超标。

只能推倒重来：**用纯 JDK 重写**（JDK 自带 HTTP Server + JDBC + 手写 Redis 协议客户端，零框架依赖），最终 jar 只有 **4.3MB**，zip 压缩后 **4.2MB**，顺利上传。

> 复盘教训：机试环境不是生产环境，**体积和依赖意识**很重要。能用标准库解决的，就别背一个框架上来。

## 核心设计：三道防线，MySQL 挂了订单也不丢

我提交的方案（也是真实落地、跑通考试系统的方案）：

```
第三方推送 ──▶ POST /api/orders/batch
                │
                ├─ ① Redis SETNX 去重（第一道防线，TTL 7 天）
                ├─ ② 内存缓存查商品名（每 30 秒从商品表刷新）
                │
                ├─ ③ 写 MySQL（INSERT IGNORE + 唯一索引，第二道防线）
                │        │
                │        ├─ 成功 → 统计入库
                │        └─ 异常/超时 → LPUSH 进 Redis pending，不阻塞
                │
                └─ ④ 后台 PendingSync 定时任务（每秒一轮）
                       ├─ 先 SELECT 1 探活 MySQL
                       ├─ RPOP 弹出一单，重新入库
                       ├─ 成功 → 累加入库统计
                       └─ 失败 → RPUSH 推回队尾，保序等下一轮
```

拆开讲：

**① Redis SETNX 去重。** 入口对每个 `order_id` 执行 `SET order:{id} 1 NX EX 604800`，抢到才继续，重复请求直接跳过。Redis 单线程 + 原子性，天然适合干这个。

**② 内存缓存商品名。** 回填商品名如果每次都查 MySQL，那 MySQL 一挂，连商品名都拿不到。所以启动时把商品 ID → 商品名加载进内存，每 30 秒刷新一次。接口只读内存，MySQL 挂不挂都不影响。

**③ INSERT IGNORE + 唯一索引。** 即使 SETNX 漏了（比如 Redis 挂了，代码里明确做了降级放行），数据库的 `order_no` 唯一索引也能挡住重复写入。Redis 挂 → 去重放行 → 唯一索引兜底，两条防线是互补的。

**④ 2 秒约束的三件套。** 这是原题最狠的地方，我用了三层保障：

- JDBC 连接/读超时设成 **1 秒 / 2 秒**——MySQL 挂了请求会立刻失败，不会傻等 30 秒默认超时
- 批次处理设 **1500ms 截止时间**——一个批次超过 1.5 秒就不再尝试写库，剩余订单全部进 pending，保证接口 2 秒内必返回
- 写库失败、超时的订单都 `LPUSH` 进 Redis pending 队列，接口**照常返回成功**

**⑤ PendingSync 异步回放。** 每秒一轮：先 `SELECT 1` 探活，MySQL 活着才 `RPOP` 弹单重试入库，成功才统计；失败 `RPUSH` 推回队尾保序。Redis 本身持久化，订单不会丢。

这套设计的核心思想：**把"MySQL 不可用"变成一种可容忍状态**——写不进库就进 Redis 排队，数据库恢复后自动补写，接口对调用方的可用性始终 100%。

## 部署交付：从 Dockerfile 到一键脚本

打包内容：`Dockerfile` + `docker-compose.yml` + `deploy.sh` + `test-exam.jar` + 部署文档。镜像基于 **eclipse-temurin:17-jre-alpine**（基础镜像小），容器加入沙箱预建的 `exam-infra` 网络，直连 `exam-mysql` / `exam-redis`。

`deploy.sh` 做了一键化：清理旧容器 → `docker compose build` → `up -d` → 每 2 秒探测一次 `/health`，最多等 60 秒，失败自动打印容器日志。考试系统的 MySQL 故障注入会暂停 MySQL 约 10 秒再自动恢复，这个窗口正好验证我的 Redis 缓冲设计。

## 结局：没做完，但收获比做完更大

最终结果：没做完。时间主要丢在两件事上——连那个根本不存在的虚拟机、重写那个 30MB 的 jar。如果时间预算合理，这套设计完全能落地演示（事实上，功能核心已经跑通）。

但这次机试让我想明白了几件事：

1. **先理解交付方式，再写代码。** 上传方式、运行环境、大小限制，这些信息比算法题更重要。
2. **时间要预算。** 90 分钟是"环境探索 + 写代码 + 打包上传 + 调试 + 演示"的 90 分钟，每一步都要留量。
3. **AI 工具帮不了环境的忙。** 题目说可以用任何 AI 工具，但 AI 再强，也解决不了安全组连不上、jar 超大小这种环境问题——这些只能靠自己的判断力。
4. **越轻越好。** 纯 JDK 不是退步，是机试场景下的最优解。
5. **2 秒这种硬约束，是方案的锚点。** 所有设计（内存缓存、超时、队列、异步）都从它长出来。

第一次机试，失败得很彻底，也值回票价。下一次，先看题目，再动手。
